# 贡献指南

欢迎贡献问题复现、功能建议、代码修复、文档和回归夹具。先在 [Issues](https://github.com/winslght/ZhiNengX-plugin/issues) 与[已知问题和路线图](ROADMAP_AND_ISSUES.md)查找相同问题，已有记录可以直接补充新证据。

## 报告问题或提建议

- 写明受影响的插件、脚本头部版本、稳定版或公测版、浏览器及脚本管理器。视觉问题请标明浅色或 Dark Reader 深色模式。
- 写清页面、操作顺序、预期结果和实际结果。比如「提交答案 → 点击想看答案 → 打开确认框后底栏变红」。
- 可附脱敏截图或最小复现。HTML 快照、报告数据可能包含昵称、头像、题目、能力进度和学习记录。公开提交前先清理个人信息，原始快照留在 `dev_resources/snapshots/inbox/`。
- 提新功能时，说明适用场景、希望改善的现有流程和可验收的预期表现。

## 开发与验证

1. Fork 并克隆仓库，从最新 `develop` 创建 `feat/*` 或 `fix/*`。分支、版本和回退规则见 [Git 流程规范](GIT_FLOW_SPECIFICATION.md)与[任务分支 SOP](GIT_DEVELOPMENT_SOP.md)。
2. 用[本地调试 SOP](DEVELOPMENT_WORKFLOW.md)配置脚本管理器，刷新知能行页面验证。开发分支上的安装版本 `@version` 由发布流程统一管理。修改美化助手供本地试用时，按[项目协作规范](../AGENTS.md)同步 DEV 版本和源码时间。
3. 根据改动选择验证。脚本先过 `node --check`。复制能力跑[浏览器回归夹具](../dev_resources/README.md)，检查公式、图片、空内容和剪贴板降级。视觉改动检查亮暗模式及切题后的状态。快照采集器可运行 `node dev_resources/snapshots/selfcheck.js`。
4. 保持改动集中，提交前核对差异。请勿提交含个人路径的调试存根、账号数据、未脱敏的快照或浏览器会话内容。

## 提交 Pull Request

1. 提交使用双语格式 `<type>(<scope>): <English description> / <中文说明>`。同一阶段的相关改动尽量合成一次有意义的提交。
2. PR 目标选择 `develop`，关联相应 Issue，说明改动前后的行为、如何验证、仍待验证的场景。界面改动可附脱敏的前后截图。
3. 需求涉及两个插件时，注明各自改动和影响。影响用户可见行为时，准备「修复」「优化」「新增」「已知问题」更新说明。没有已知问题时明确写「暂无已知问题」，未实测的场景单独交代。
